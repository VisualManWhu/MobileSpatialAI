# Recon3D 第二期（前半段）：识别物体、物体表、飞过去高亮 — 设计

日期：2026-11-07
状态：草稿，待用户确认
上位文档：`2026-11-01-recon3d-design.md` §5.4（第二期）。本文只做其中**前半段**：服务端认物体出物体表，手机端看表、点一项镜头飞过去并高亮。后半段（Claude 问答）另写。

## 1. 要做什么、为什么

重建好的房间现在只能"看"。这一步让它"认得"里面的东西：服务端在关键帧上跑开放词汇检测 + 分割，把多帧里的同一个物体合成一个 3D 物体，把高斯点归到物体名下，产出一张**物体表**；手机在查看页列出"椅子 ×2、显示器 ×1、杯子 ×3…"，点一项镜头飞过去、该物体高亮、其余调暗。

先只做到这里，是为了在接 LLM 之前，用肉眼确认"认得准不准、数得对不对"——上位文档的反目标第一条是"数数不准即失败"，物体表是数数的根基。

## 2. 目标 / 非目标

### 目标
- 对已完成重建的任务，按需（用户点按钮）生成物体表，笔记本（RTX 4060 8 GB）上 **5 分钟内**完成（1100 帧的拍摄）。
- 桌面常见物品（杯、瓶、书、遥控器、显示器、键盘、鼠标、植物、箱子…）和大件家具（桌、椅、门、窗、灯）大多数能认出，同一物体不重复计数。
- 手机列表 → 点一项 → 1 秒内飞到并高亮。
- 空间关系（上/里/旁/左右）这次就算出来存进表，供后半段直接用；手机端这次不显示。

### 非目标（这次不做）
- LLM 问答、自然语言输入。
- 在 3D 场景里直接点选物体。
- 用户在 App 里编辑词表。
- 重建完自动跑识别（用户决定：按需点）。
- 把识别结果带到"改用高精重算"后的新任务（新任务要重新点识别）。
- 第三期的影子物体。

## 3. 用户看到的流程

1. 查看 3D 页，右上角（Compose 层，和漫游按钮不冲突：漫游按钮在网页里）出现按钮 **「识别物体」**（该拍摄还没有物体表时）。
2. 点击 → 按钮变成状态文字 **「识别物体 (检测) 42%」**，阶段依次：检测 → 合并 → 归属 → 截图。期间可以继续转场景。离开页面再回来状态仍在（和重建进度一样轮询）。
3. 完成后服务端产物自动下载到手机，按钮变 **「物体 (12)」**。失败则显示 **「识别失败：<原因>」**，按钮变「重试识别」。
   - **重新识别**（开发者定）：长按「物体 (N)」弹出「重新识别」；期间按钮显示进度，**旧的物体表照常可用**，新结果下载完成后才整体替换本地 `objects/`。
4. 点「物体」→ 底部弹出列表：按类别分组，组头"椅子 ×2"，每项一张小缩略图 + "椅子 1"。点一项 → 列表收起，镜头飞到该物体前方，它保持原色，其余高斯调暗至约 15% 不透明度并去色；屏幕底部出现一条 **「椅子 1 · 取消高亮」**，点它恢复。再次点「物体」可换一个。
5. 漫游模式下同样可用（flyTo 本就在漫游里生效，高亮与控制方式无关）。
6. 服务端状态页多一列「物体」：无 / 排队 / 识别中 x% / 12 个 / 失败。

## 4. 服务端

### 4.1 任务模型
- 物体识别是**挂在已有重建任务下的第二种工作**，不是新任务。同一个 worker 队列按序执行（重建和识别不会同时占显存）。
- `status.json` 增加一块：
  ```json
  "objects": {"state": "none|queued|running|done|failed", "progress": 0.0, "message": "识别物体 (检测)", "count": 12}
  ```
  任务主 `state` 保持 `done`，手机端查看场景不受影响。
- 接口（前缀 `/api/v1`，写进 `docs/api.md`）：
  - `POST /jobs/{id}/objects` → 202，`objects.state=queued`。前提：任务 `state == done` 且有 `capture.zip`，否则 409「任务尚未完成」；已在 queued/running → 409「正在识别」；已 done → 重新识别（覆盖）。
  - `GET /jobs/{id}` 的返回里带上述 `objects` 块。
  - `GET /jobs/{id}/objects.zip` → 产物包（见 4.5）；没有 → 404。
  - `DELETE /jobs/{id}` 已删整个目录，自然带走产物。
- 服务重启时 `queued/running` 的识别回到 `queued`（和重建任务一致）。

### 4.2 输入
- `capture.zip`（已保留在任务目录）：图片、ARCore 位姿、内参。**不用拍摄包里的深度图**（开发者定，见 4.4 的"深度来源"）。
- 位姿：高精任务用 `poses_cv.npy`（优化后的位姿，和训练用的一致），快速任务用 ARCore 位姿。**必须和训练时的位姿一致**，否则高斯点投影对不上。
- `scene.splat`：高斯点归属按**导出顺序**计算（`export_splat` 按重要性排序过），产物里的索引即 `.splat` 里的序号，手机端查看器直接按序号用。
- 帧采样：相邻关键帧几乎一样，取每 k 帧一张使帧数 ≤ 240（k = ceil(n / 240)）。

### 4.3 模型（开发者选，用户可推翻）
- 检测：**Grounding DINO tiny**（`IDEA-Research/grounding-dino-tiny`，transformers 4.57 已含）。实测 1920×1080 单帧 0.40 s，峰值 2.3 GB。
- 分割：**SAM 2.1 hiera-small**（`facebook/sam2.1-hiera-small`，transformers `Sam2Model`），以检测框为提示出 mask。实测 0.17 s/帧，峰值 1.4 GB。需新增依赖 `torchvision==0.19.1`（配 torch 2.4.1，cu124 索引）。
- 模型权重首次使用时从 Hugging Face 下载（用户网络可达），缓存在服务端 venv 所在机器的 HF cache；安装文档写一句"第一次识别会多等一两分钟下载模型"。
- 词表：`server/recon3d/objects/vocab.py`，固定约 40 类室内物体，每类英文提示词 + 中文显示名，例如 cup/杯子、bottle/瓶子、book/书、remote control/遥控器、chair/椅子、table/桌子、monitor/显示器、laptop/笔记本电脑、keyboard/键盘、mouse/鼠标、phone/手机、box/箱子、bag/包、lamp/灯、plant/植物、whiteboard/白板、door/门、window/窗、trash can/垃圾桶、pen/笔、sofa/沙发、bed/床、pillow/枕头、shelf/架子、cabinet/柜子、tv/电视、speaker/音箱、headphones/耳机、clock/钟、picture frame/相框、curtain/窗帘、mirror/镜子、fan/风扇、printer/打印机、backpack/背包、shoes/鞋、towel/毛巾、sink/水槽、refrigerator/冰箱、microwave/微波炉。阈值：框 0.35、文本 0.25。词表过长时分批提示（每批 ≤ 20 类）。

### 4.4 算法
**深度来源**（开发者定）：每张采样帧的像素深度**由训练好的高斯渲染得到**（`scene.ply` 载入 gsplat，按该帧位姿 / 内参渲染深度，半分辨率），不用 ARCore 深度图。理由：ARCore 深度分辨率低、在显示器 / 玻璃 / 深色表面有洞、raw 深度还滞后于图像帧，会让显示器、窗、黑色物体拿不到 3D 点而被丢掉；渲染深度和高斯点本身严格一致，覆盖完整，240 帧半分辨率渲染十几秒。副作用：不再有"拍摄包没有深度"的失败情形。

1. **检测 + 分割**（进度 0 → 0.6）：每张采样帧跑 GDINO 得框和类别，SAM 2 得 mask。记录 (帧, 类别, 分数, 框, mask)。**同一帧内先做 NMS**（跨类别，IoU ≥ 0.7 去重，保留高分），处理词表分批带来的重复框。
2. **合并成 3D 物体**（0.6 → 0.75）：每个 mask 与渲染深度相交，反投成相机系 3D 点再变到世界系，均匀下采样到 ≤ 2000 点。贪心合并规则（开发者定）：
   - **同一帧里的两个检测永远不合并**（两只挨着的杯子就是两只）。
   - 同类：一方 ≥ 30% 的点落在另一方点集 5 cm 内，或 3D 包围盒 IoU ≥ 0.3 → 同一物体。
   - **跨类**（显示器/电视、包/背包、架子/柜子、沙发/椅子这类近义会逐帧跳变）：允许合并，但门槛更严——一方 ≥ 60% 的点落在另一方 5 cm 内，且 3D 包围盒 IoU ≥ 0.5。
   - 只在 **1 帧**出现的物体丢弃（压误检）；至少 2 帧。物体中心 = 点集中位数，包围盒 = 各轴 5–95 分位。类别 = 该物体各帧检测分数加权最多的类别（跨类合并后才有意义）。
3. **高斯点归属**（0.75 → 0.95）：读 `scene.splat` 的中心位置（N 点，导出顺序）。对每张采样帧：把高斯中心投到像素，落在某物体 mask 内、且高斯深度与该像素渲染深度之差 < 0.1 m + 5% 深度 → 给该物体投一票。高斯归票数最多的物体，票数 ≥ 2 才算；另要求高斯中心在该物体包围盒外扩 10 cm 之内。其余为 0（无物体）。GPU 上做（N≈10⁶ × 240 帧的投影是矩阵乘，秒级）。
4. **代表截图**（0.95 → 1.0）：取分数 × mask 面积最大的那次检测，框外扩 15% 裁下，长边缩到 256，JPEG。
5. **空间关系**（在 4 中顺带）：对中心距离 < 1.5 m 的物体对算：
   - `on`：A 底面在 B 顶面之上 10 cm 以内，且 A 的水平中心在 B 的水平包围盒内。
   - `in`：A 包围盒体积 ≥ 90% 在 B 包围盒内。
   - `next_to`：水平间隙 < 0.3 m 且竖直范围有重叠。
   - `left_of` / `right_of`：以 home 视角（第一帧朝向）为参照。
   存成 `[{"a": 3, "rel": "on", "b": 7}]`。

### 4.5 产物 `objects.zip`
放在任务目录 `objects/` 下，打成 zip 供手机一次下载：
- `objects.json`
  ```json
  {"version": 1, "job_id": "…", "frames_used": 225, "gaussians": 983112,
   "objects": [{"id": 1, "label": "chair", "label_zh": "椅子", "score": 0.64, "views": 17,
                "center": [x, y, z], "bbox": {"min": [..], "max": [..]}, "gaussian_count": 23410,
                "thumb": "thumbs/1.jpg"}],
   "relations": [{"a": 3, "rel": "on", "b": 7}]}
  ```
  `id` 从 1 起连续；坐标是场景世界系（和 `.splat` 一致）。
- `objects.bin`：N 个 little-endian **uint16**，第 i 个是 `.splat` 第 i 个高斯所属物体 id，0 = 无。1 M 高斯 ≈ 2 MB，查看器直接当纹理用。
- `thumbs/{id}.jpg`。

### 4.6 代码位置
`server/recon3d/objects/`：`detect.py`（GDINO + SAM 2 封装，惰性加载）、`render_depth.py`（gsplat 载入 `scene.ply` 渲染各帧深度）、`merge.py`（纯 numpy，可单测）、`assign.py`（torch）、`relations.py`（纯 numpy，可单测）、`thumbs.py`、`pipeline.py`（`run_objects(job_dir, profile, on_progress)`）。`jobs/worker.py` 增加第二种工作类型；`jobs/store.py` 增加 `objects` 状态读写与 `request_objects(job_id)`。

### 4.7 失败与资源
- 显存不足 → `失败：显存不足`（与重建一致的措辞）；模型下载失败 → `失败：模型下载失败，请检查网络`。
- 跑完立即释放模型和显存（下一个重建任务要用满 8 GB）。
- 中间产物不落盘（mask 只在内存里，按帧处理完即丢）。

## 5. 手机端

### 5.1 数据
`CaptureRecord` 增加：`objectsState`（`none|queued|running|done|failed`）、`objectsProgress`、`objectsMessage`、`objectsCount`、`objectsPath`（本地目录，解压后的 `objects.zip`，与 `scene.splat` 同级 `objects/`）。删除拍摄 / 彻底删除时一并清理。

### 5.2 流程
- 点「识别物体」→ `POST /jobs/{jobId}/objects` → 进入轮询（复用 `UploadViewModel` 的轮询机制，读 `GET /jobs/{id}` 里的 `objects` 块）→ `done` 时下载 `objects.zip` 解压到 `objectsPath` → 状态 `done`。
- 识别失败不影响场景查看；`objectsState=failed` 时按钮为「重试识别」。
- 重新识别（长按）期间 `objectsPath` 不动，列表仍可用；新 zip 下载解压到临时目录成功后再原子替换。重新识别失败 → 提示失败，旧表保留。
- 任务在服务端已不存在（404）→ 提示「服务端任务已不存在，需重新上传」，和现有 `MSG_JOB_GONE` 一致。

### 5.3 查看器（`viewer-web`）
- JS API：`loadObjects(url)`（取 `objects.bin`，建每高斯 id 纹理）、`highlightObject(id)`（id > 0 高亮该物体、其余调暗去色；0 恢复）。`WebViewAssetLoader` 的 `/scene/` 只放行 `scene.splat`，需放行 `objects.bin`（`ScenePathPolicy`）。
- 调暗实现：**首选** Spark 的逐高斯修改器（dyno `objectModifier`，按 splat 序号查 id 纹理，比较 uniform `selectedId`，改 rgba）；若 spike 发现不可行，**退路**是在 JS 里改 `.splat` 字节里的 rgba 后重建 `SplatMesh`（10 MB 场景亚秒级）。计划第一项先做这个 spike。
- 飞行目标：相机位置 = 物体中心 + 水平方向单位向量（从中心指向当前相机位置的水平投影；退化时用 home 朝向反向）× 距离，距离 = max(包围盒对角线 × 1.5, 0.8 m)，高度 = 中心高度 + 0.3 × 距离；lookAt 物体中心；时长 1 s。

### 5.4 界面
- Compose 层：查看页右上角一个 `AssistChip` 风格按钮（「识别物体」/「识别物体 (检测) 42%」/「物体 (12)」/「重试识别」）；网页里的「漫游」按钮为避开它下移到右上第二个位置。
- 物体列表：`ModalBottomSheet`，`LazyColumn`，组头「椅子 ×2」，项：48 dp 缩略图 + 「椅子 1」。
- 高亮中：底部居中一条半透明条「椅子 1 · 取消高亮」。
- 所有文案中文。

## 6. 验收（写进 `docs/acceptance/phase1.md` 新章节或 `phase2.md`）
1. 办公桌场景 `40a80bd6c17f`：点「识别物体」，5 分钟内完成；状态文字按阶段变化；状态页「物体」列同步。
2. 列表里的类别与数量和真实桌面对照，大多数一致；没有同一物体被拆成两个；缩略图确实是那个物体。
3. 点 3 个不同物体：镜头各自飞到正确位置，高亮的是那个物体，其余调暗；「取消高亮」恢复。
4. 漫游模式下重复第 3 条。
5. 关掉查看页再进，「物体 (N)」仍在，无需重新识别；杀掉 App 也一样。
6. 把该拍摄「改用高精重算」后，新任务上按钮回到「识别物体」。
8. 长按「物体 (N)」重新识别：期间旧列表仍能点、能高亮；完成后数量更新。
9. 显示器 / 窗这类 ARCore 深度拿不到的物体也出现在列表里并能高亮（渲染深度的意义所在）。
7. 服务端日志里有每阶段耗时。

## 7. 留给实现者的决定
- 高斯点归属在 GPU 上的分块大小；合并时点云的下采样方式。
- 词表分批的具体切法；缩略图裁切细节。
- 状态页「物体」列的具体渲染。
- 测试：`merge.py`、`relations.py`、`objects.bin` 编解码、API 状态机用纯 CPU 单测；检测/分割与整条链用 `@pytest.mark.gpu` 对一个小合成场景或真实拍摄包的前 20 帧跑。
