# Recon3D 设计文档

日期：2026-11-01
状态：草稿，待用户确认

## 1. 这是什么、为什么做

用户想要一个类似 KIRI Engine 旗下 Remy 的 App，装在自己的 **Google Pixel 10 Pro** 上：拿手机绕房间拍一圈，得到一个可以浏览的 **3D Gaussian Splatting（3DGS）房间场景**。在这个基础上还要能做两件事：

1. **问答并指出物体**：用户问"桌子上面有几只杯子"或"杯子旁边有什么"，App 给出正确答案，镜头自动飞到对应物体，并高亮显示。
2. **重访并发现变化**：过几天再拍一次同一个房间，App 自动在 3D 场景里标出多了什么、少了什么。

和 Remy 一样，重建放在电脑或服务器上算，不要求在手机本地完成（用户已确认）。

**用户背景**：没有 Android 开发经验，也没有 Python/PyTorch 经验。所以整套东西必须能照着文档一步步装起来、跑起来，命令越少越好。

**使用范围**：只给用户自己用，不上架应用商店，不做多用户和账号。

## 2. 分期

三期按顺序做。每一期做完都能单独使用，后一期建立在前一期之上。

| 期 | 内容 | 做完以后用户能做什么 |
|----|------|------|
| 第一期 | 拍摄 App + 上传 + 3DGS 重建 + 手机端浏览 | 拍一个房间，几十分钟后在手机上转着看 3D 场景 |
| 第二期 | 认物体 + 物体表 + 问答 + 飞过去高亮 | 对重建好的房间提问，得到答案并看到物体被高亮 |
| 第三期 | 重访 + 对齐 + 变化检测 | 再拍一次，自动标出新增和消失的物体 |

本文档三期都写，第一期最细。

## 3. 目标、非目标、反目标

### 目标
- 房间级场景（典型卧室、客厅，约 10 到 30 m²）能稳定重建出可以辨认的 3DGS 场景。
- 拍摄过程有清晰的箭头引导，普通人照着做就能拍好。
- 问答能**正确数数**、能回答简单空间关系（上面、旁边、里面、左右），而且能把答案对应的物体在 3D 里指出来。
- 重访能发现杯子大小及以上物体的增减。

### 非目标（现在不做）
- 手机本地完成重建或训练。
- 动态场景（拍摄时有人或宠物走动）。
- 语音提问（先打字，以后再加）。
- 拍摄时实时在相机画面里标注物体或变化。
- 把"物体移动了"单独识别成"移动"（先当作一个消失加一个新增）。
- 上架、多用户、账号、分享。
- iOS。

### 反目标（即使能跑也算失败）
- 数数不准。例如"几只杯子"答错，或者高亮了错误的物体。这是第二期选"物体表"而不是"每个高斯点挂语义特征"的原因。
- 用户装不起来。如果需要用户自己排查 CUDA 编译、环境冲突之类的问题，就算失败。
- 拍摄时需要用户懂技术，比如自己判断哪里没拍到。

## 4. 约束

- **手机**：Google Pixel 10 Pro，支持 ARCore（含 Depth API）。App 通过 USB 或无线调试安装（sideload），不走应用商店。
- **笔记本**（默认的计算端）：Windows 11，NVIDIA RTX 4060 Laptop GPU **8 GB 显存**，32 GB 内存，驱动 577.02。
- **服务器**（笔记本不够时用）：NVIDIA RTX A6000 Ada，48 GB 显存，**Ubuntu**，放在**实验室**，能连 Wi-Fi，和用户家里不在同一个网络。（用户决定）
- **网络**：用户在**德国**，Claude API、Hugging Face、Docker Hub、GitHub、PyPI、Google Maven 都能正常访问，不需要国内镜像。（用户确认）
  - 在家时：手机和笔记本在同一个 Wi-Fi 下。
  - 在实验室时：手机可以和服务器连同一个 Wi-Fi，直接把任务发给服务器。
  - **跨网络转发（Claude 决定，开发者可调整）**：手机只认一个"计算端地址"。在家时如果某个任务笔记本算不动（比如第二期的语义训练），由笔记本把任务转发到实验室服务器，算完再取回结果，手机这边无感知。转发方式（SSH 隧道、VPN、对象存储中转等）由开发者根据实验室网络条件决定，**前提是用户对服务器有 SSH 访问权限，这一点尚未确认**，开发者应先向用户核实；如果无法跨网络访问，退化为"只在实验室时使用服务器"。
- **大语言模型**：调用云端 API（默认 Claude），不在本地跑。用户需要自己提供 API key。
- **服务端代码**必须在笔记本和服务器上都能跑，只通过配置切换（例如降低分辨率、限制高斯点数量）。

## 5. 已经定下来的做法

下面标"（用户决定）"的是用户明确说过的，标"（Claude 决定）"的是我替用户做的选择，用户可以推翻。

### 5.1 总体结构
- 手机负责**采集和浏览**，计算端负责**重建、认物体、问答编排、变化检测**。（用户决定：可以放到电脑或服务器上算）
- 手机通过局域网 HTTP 和计算端通信，计算端提供一个简单的任务接口：上传拍摄包、查询进度、下载结果、提问。（Claude 决定）

### 5.2 手机 App
- Android 原生，Kotlin + Jetpack Compose，用 **ARCore** 获取每一帧的相机位姿、相机内参和深度。这样服务端不用跑 COLMAP 反推相机位置。房间里白墙多，COLMAP 容易失败，这一点很关键。（Claude 决定）
- **拍摄引导：风格 A，"大箭头 + 进度环"**，叠加在**实时相机画面**上（用户决定，已看过草图）：
  - 顶部显示三个阶段标签：① 转圈、② 上下、③ 补拍；当前阶段高亮，完成的打勾。
  - 顶部有一个进度环，显示当前阶段的完成百分比。
  - 屏幕中央一个大箭头，指出接下来往哪个方向转或走。
  - 底部一行主提示加一行副提示，例如"站在房间中央，慢慢向右转 / 保持手机与胸口同高"。
  - 底部是录制按钮。
  - **阶段①**：站在房间中央原地转一圈。用 ARCore 的偏航角（yaw）覆盖了多少来算进度。
  - **阶段②**：上下扫动，覆盖天花板和地面。用俯仰角（pitch）覆盖范围来算进度。
  - **阶段③**：走动补拍漏掉的区域。箭头指向漏拍最多的方向，"漏拍"的具体判断方法由开发者决定。
  - 拍得太快（运动模糊）或 ARCore 跟丢时，要提示用户放慢或回到之前的位置。
- **浏览 3D**：第一版在 App 里用 WebView 嵌一个网页版 3DGS 查看器，必须支持：触摸转动和缩放；用程序控制镜头平滑飞到指定位置；按物体编号高亮一组高斯点、其余调暗；显示半透明的"影子"物体（第三期用）。用哪个网页查看器由开发者选。（Claude 决定）
- App 内保存一个房间列表。每个房间可以有多次拍摄：第一次叫"建模"，之后的叫"重访"。

### 5.3 第一期：重建
- 拍摄时按一定间隔（或根据移动距离）保存关键帧：JPEG 图片、ARCore 位姿、内参、深度图（有的话），打包上传。拍摄包的具体格式由开发者定，但要写成文档，并且带版本号。
- 服务端把 ARCore 坐标转换成训练用的格式，用 ARCore 的深度或特征点云初始化高斯点，然后训练 3DGS。训练库默认用 **gsplat**，因为它省显存，适合 8 GB 的笔记本。（Claude 决定）
- 如果 ARCore 的位姿有漂移，导致场景出现重影，可以在服务端加一步位姿优化。是否需要由开发者实测决定。
- 训练完导出一个手机端查看器能加载的压缩格式，回传给手机。
- 手机上要能看到任务进度：上传中、排队、训练中（百分比）、完成、失败（附原因）。

### 5.4 第二期：认物体和问答
- **用物体表，不用逐点语义特征**（Claude 决定，理由见反目标第一条：数数要准）。
- 服务端在关键帧上跑现成的**开放词汇检测和分割模型**，不需要用户标注数据。具体用哪个模型由开发者选。再借助位姿和深度把多张图里的同一个物体合并成一个 3D 物体，并把对应的高斯点归到这个物体编号下。
- 物体表每一项至少包含：编号、类别名、3D 包围盒、中心点、对应的高斯点集合、一张代表性截图。
- 物体之间的关系（上面、旁边、里面、左右等）用几何规则算出来存进表里，不让大语言模型去猜几何关系。
- **问答流程**：手机发送文字问题 → 服务端把问题和物体表交给大语言模型 → 模型返回结构化结果，即答案文本加相关物体编号 → 手机显示答案、镜头飞到这些物体、高亮它们、其余调暗。（用户决定：要同时给答案、飞过去、高亮）
- 先支持打字提问。（Claude 决定，用户已认可）

### 5.5 第三期：重访和变化检测
- 用户在房间列表里选"重访"，按同样的箭头引导再拍一次，可以拍得短一些。（用户已认可）
- **每次重访永远和最初那次建模比**，不和上一次重访比。所有重访都对齐到建模那次的坐标系，物体的"新增 / 消失"也都相对建模那次的物体表来算。这样对齐误差不会一次次累积。（用户决定）
- **对齐**：ARCore 不能跨次记住坐标，所以服务端要把新拍摄对齐到旧场景。思路是用画面特征把新关键帧和旧关键帧匹配，算出新拍摄在旧场景里的位姿，再用深度点云做精细对齐。具体方法由开发者定。
- 对新拍摄重建 3DGS（在旧场景的坐标系下），再跑一遍第二期的认物体，得到新的物体表。（Claude 决定：要在 3D 里显示"新增"的物体，就必须有新的重建）
- **对比**：按类别和 3D 位置把新旧物体一一配对。没配上的旧物体标为"消失"，没配上的新物体标为"新增"。
- **显示**：打开新场景，新增物体**绿色高亮**；消失的物体用旧场景里它对应的高斯点，在原位置画一个**半透明红色影子**。旁边给一个变化列表，点某一项镜头就飞过去。（用户已认可）
- 光线变化、椅子稍微挪动这类小差异不算变化。阈值由开发者调。
- 结果在服务端处理完后才显示，不要求实时。（用户已认可）

## 6. 成功标准（Claude 拟定，可调整）

- **第一期**：一个约 15 m² 的卧室，按引导 3 分钟内拍完；在笔记本上 30 分钟内重建完成；在手机上浏览流畅，家具和桌上的物品都认得出来。
- **第二期**：对桌面上的常见物品（杯子、书、遥控器、瓶子等），"有几个 X"和"X 旁边有什么"这类问题，大多数时候答对，并且高亮的是正确物体；从提问到镜头飞过去在 10 秒左右。
- **第三期**：在桌上加一个杯子或拿走一个杯子，重访后能被标出来；没动过的东西不会被误报成变化。

## 7. 对开发者的额外要求（因为用户没有开发经验）

- 提供一份从零开始的中文安装文档：在 Pixel 上打开开发者模式并安装 App；在 Windows 笔记本上装好服务端；在服务器上部署。
- 服务端要做到一条命令启动。用户不应该需要手动编译 CUDA 扩展或排查 Python 环境冲突。用 WSL2、Docker 还是预编译包，由开发者决定，但必须在 Windows 笔记本和 Ubuntu 服务器上都能可靠工作，最好两边共用同一套环境（例如同一个 Docker 镜像）。
- 手机 App 里要能填写计算端地址（IP 和端口），最好能在局域网里自动发现。
- 出错时，App 和服务端都要给出用户看得懂的提示。

## 8. 留给开发者决定的事

- 网页 3DGS 查看器、开放词汇检测和分割模型、特征匹配方法的具体选型。
- 拍摄包格式、物体表格式、API 接口的具体设计。
- 关键帧的采样策略、分辨率，以及笔记本和服务器两档配置的具体参数。
- 代码仓库结构（建议一个仓库，里面分 `android/`、`server/`、`docs/`）。
- 测试策略。
